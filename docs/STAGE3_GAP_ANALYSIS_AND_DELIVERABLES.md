# Promptory 3차 기준 비교분석 및 산출물 정리

기준 문서(3차 프로젝트 안내)와 현재 저장소 상태를 비교해,  
**이미 충족한 항목 / 보완이 필요한 항목 / 제출 산출물 상태**를 한 번에 정리한 문서다.

---

## 1) 프로젝트 한 줄 판정

현재 Promptory는 3차 핵심 목표인 아래 흐름을 코드 기준으로 충족한다.

`사용자 → 서비스 서버(Django/DRF) → DB(PostgreSQL) → 화면(Template+JS)`

즉, **기능 중심 서비스 골격은 완성 상태**이며, 발표/제출 관점에서 남은 일은 주로 문서·시연 산출물 보강이다.

---

## 2) 3차 필수 구조 비교

| 기준 | 현재 상태 | 판정 |
|---|---|---|
| 메인 서비스 서버 | Django + DRF + Template 분리 구조 | 충족 |
| 데이터 저장 구조 | PostgreSQL 전환 완료, 모델 관계 설계 완료 | 충족 |
| 사용자 흐름 | 회원가입/로그인/JWT/CRUD/상호작용/화면 렌더링 연결 | 충족 |
| 데이터 흐름 완성 | API + DB + UI end-to-end 동작 | 충족 |

## 3) 필수 기능 체크 (기준 A)

### A-1. 기본 서비스 필수 항목

| 기능 | 현재 상태 | 근거 |
|---|---|---|
| 회원가입 | 구현 완료 | `accounts` register API + serializer validation |
| 로그인/로그아웃 | 구현 완료 | SimpleJWT + logout blacklist |
| 핵심 도메인 CRUD | 구현 완료 | `prompts` CRUD + 권한 |
| 분류(카테고리 1단계) | 구현 완료 | `Category` + 목록/상세 표시 |
| 검색(단일 필드) | 구현 완료 | `search_fields` (`title`, `description`) |
| 페이지네이션 | 구현 완료 | DRF PageNumberPagination, PAGE_SIZE=12 |
| 관리자 페이지 | 구현 완료(계정 준비 필요) | admin 등록/커스터마이징, 계정은 환경별 생성 필요 |

### A-2. 선택 기능(가산점 가능)

구현되어 있는 항목:
- JWT(Access/Refresh/재발급/블랙리스트)
- 파일 업로드(정책 포함)
- 댓글(+대댓글 구조)
- 좋아요/북마크 토글
- 태그
- 검색 고도화(필터/정렬/다중 조건)
- 페이지네이션 고도화(파라미터 기반 정렬/필터)
- 관리자 페이지 커스터마이징
- Soft Delete
- 권한 처리 고도화(작성자 권한)

## 6) 기준 대비 보완 필요(실제 수정/추가 권장)

아래 항목은 기능보다는 **발표/제출 완성도** 영역이다.

1. **ERD 산출물 고정**
   - 현재 코드상 모델은 충분하지만, 제출용 ERD 파일(이미지/문서)이 저장소에 없다.
2. **아키텍처 다이어그램 고정**
   - 사용자→Django Template/DRF→PostgreSQL 흐름을 1장으로 고정 필요.
3. **발표 시연 시나리오 문서화**
   - 10분 발표 흐름(로그인→CRUD→상호작용→관리자)을 체크리스트화 필요.
4. **운영 체크 항목 리허설**
   - 발표 직전 500/권한/계정/데이터 재확인 체크를 1회 실행.

## 7) 잘못됐거나 오해하기 쉬운 포인트 정정

- "앱 분리는 모델 기준으로 해야 한다" → **아님**  
  현재처럼 도메인 책임(`accounts/prompts/interaction`) 기준이 맞다.

- "파일 업로드는 파일 자체를 DB에 저장해야 한다" → **아님**  
  현재처럼 파일은 스토리지, DB에는 경로/메타 저장이 맞다.

- "Soft Delete는 선택이라 없어도 된다" → 3차 기준상 가산점 성격이지만  
  Promptory는 이미 적용되어 있어 강점으로 발표 가능.

## 8) 제출 산출물 패키지 (한 번에 준비할 목록)

아래 5개를 기준으로 제출 파일을 구성하면 안전하다.

### 8-1. 필수 산출물

1. **ERD 1장**
   - 필수 엔티티: `CustomUser`, `Prompt`, `Category`, `Tag`, `PromptFile`, `Comment`, `Like`, `Bookmark`
2. **아키텍처 1장**
   - 흐름: Browser(Template+JS) → DRF API → PostgreSQL
   - 인증: JWT Access/Refresh
3. **API 명세**
   - 엔드포인트, 메서드, 요청 예시, 응답 예시
4. **실행 가이드**
   - 로컬(PostgreSQL) + Docker Compose 실행 순서
5. **관리자 가이드**
   - `createsuperuser`, admin URL, Soft Delete 확인 방법

### 8-2. 권장 추가 산출물(발표 점수 방어용)

- 인증 흐름 다이어그램(텍스트 가능)
- 업로드 정책 문서(확장자/용량/저장 경로)
- 검색/필터/정렬/페이지네이션 파라미터 표
- interaction 앱 역할 정의(댓글/좋아요/북마크 정책)

## 9) 발표 직전 실행 체크리스트 (실행형)

1. `python manage.py check`
2. `python manage.py test`
3. 회원가입 → 로그인 → 프롬프트 생성/수정/삭제(Soft Delete) 시연
4. 댓글/좋아요/북마크 시연
5. 카테고리/검색/필터/페이지네이션 시연
6. admin 로그인 + 핵심 모델 관리 + Soft Delete 상태 확인
7. 발표용 계정/관리자 계정/샘플 데이터 최종 점검

---

## 10) 최종 결론

Promptory는 3차 기준에서 **핵심 기능/구조/DB 흐름이 모두 구현된 상태**다.  
남은 리스크는 구현 부족이 아니라, **산출물(ERD/아키텍처) 고정 및 리허설 문서화 부족**이다.

따라서 현재 단계의 우선순위는:

1) 기능 추가보다  
2) 제출 산출물 정리 + 발표 시연 안정화  

로 두는 것이 가장 효율적이다.
