- 검색 / 페이지네이션 / 관리자 페이지가 유지되는지

핵심 설명:

```
3차 = 사용자 기능 + 데이터 흐름 완성
4차 = 기존 데이터 흐름에 AI + 비동기 + 운영 구조 추가
```

## 4. 비동기 처리 설명

AI 처리는 시간이 오래 걸릴 수 있으므로, 4차에서는 비동기 처리 구조가 중요합니다.

반드시 설명할 내용:
- Celery를 왜 사용하는지
- Redis가 어떤 역할을 하는지
- task가 언제 생성되는지
- task 상태가 어떻게 변하는지
- 실패 시 FAIL 상태와 에러 메시지가 저장되는지
- task 상태 확인 API가 있는지

필수 상태값:

```
PENDING     → 요청됨
PROCESSING  → 처리중
SUCCESS     → 완료
FAIL        → 실패
```

발표에서 반드시 보여야 하는 흐름:

```
사용자 요청
  ↓
Django에서 원본 데이터 저장
  ↓
Task 생성 후 task_id 반환
  ↓
Celery Worker가 백그라운드에서 FastAPI 호출
  ↓
AI 결과 DB 저장
  ↓
Task 상태 SUCCESS 또는 FAIL 변경
  ↓
사용자가 상태 조회 API 또는 화면에서 결과 확인
```

상태 조회 API 예시:

```http
GET /tasks/{task_id}/status/
```

## 5. 데이터베이스 확장 구조 설명

4차 데이터베이스의 핵심은 기존 구조를 유지하면서 AI 결과와 Task 데이터를 확장하는 것입니다.

반드시 설명할 내용:
- 핵심 도메인 모델
- AI 분석 결과 모델
- 추천 / 유사도 결과 모델이 있다면 그 관계
- Task 모델
- 실패 로그 또는 에러 메시지 저장 구조

권장 구조:

```
User
  ↓
핵심 데이터
  ↓
 ├─ 파일 / 댓글 / 좋아요 / 태그
 ├─ AI 분석 결과
 ├─ 추천 / 유사도 결과
 └─ Task
```

설명 포인트:
- AI 결과는 원본 데이터를 덮어쓰지 않는다.
- AI 결과는 이력 또는 확장 데이터로 저장한다.
- Task는 요청과 처리 상태를 추적하기 위한 운영 데이터다.

## C. 발표 감점 기준

| 감점 항목 | 감점 |
|---|---:|
| 실행 불가 상태로 발표 진행 | -10 |
| 핵심 AI 기능 시연 불가 | -10 |
| FastAPI 서버 분리 없이 Django 내부에서만 AI 처리 | -5 ~ -10 |
| Celery / Redis 비동기 구조가 없거나 설명 불가 | -5 ~ -10 |
| task 상태 관리가 없거나 상태 확인 불가 | -5 |
| AI 결과가 DB에 저장되지 않음 | -5 |
| 핵심 시연 중 500 오류 발생 | -5 ~ -10 |
| Docker Compose 실행 불가 | -5 |
| ERD / API 명세 / 실행 문서 / 아키텍처 구조도 중 1개 누락 | 항목당 -3 |
| 발표 시간 초과 또는 발표 흐름 붕괴 | -2 ~ -5 |
| 구조 설명 없이 기능만 나열 | -3 |
| 본인이 구현한 범위와 시연 범위가 불일치 | -3 ~ -5 |
| 발표가이드에 명시된 필수 범위와 실제 시연 범위가 다름 | -3 ~ -5 |

가산점 적용 규칙:
- 구현 + 발표 시연 + 설명이 모두 확인된 경우만 반영합니다.
- 단순히 코드만 존재하거나 발표에서 설명하지 못하면 가산점으로 인정하지 않습니다.
- 가산점 총합은 최대 20점까지만 인정합니다.
- 선택 기능이 많더라도 필수 구조가 미완성인 경우 높은 평가를 받을 수 없습니다.
