
체크 방법
- `[ ]` 미확인 / 미구현
- `[x]` 확인 완료 / 발표 가능

주의사항
- 체크리스트에 `[x]` 표시한 항목은 발표에서 실제로 시연 가능해야 합니다.
- 체크한 내용과 실제 발표 내용이 다를 경우 감점될 수 있습니다.
- 자가점검은 `코드가 있다`가 아니라 `실제로 동작한다`를 기준으로 체크합니다.
- 4차 프로젝트는 기능 개수보다 사용자 입력 → 서버 처리 → DB 저장 → AI 분석 → 비동기 처리 → 결과 저장 → 화면 출력 → 모니터링으로 이어지는 전체 흐름이 실제로 연결되어 동작하는지를 더 중요하게 봅니다.

## 5. 비동기 처리 자가점검

### 5-1. Celery + Redis 구성

- [ ] Redis가 메시지 브로커로 실행된다.
- [ ] Celery Worker가 실행된다.
- [ ] Django에서 Celery task를 호출할 수 있다.
- [ ] Celery 로그에서 작업 실행을 확인할 수 있다.
- [ ] AI 분석 작업이 백그라운드에서 처리된다.

### 5-2. Task 생성 구조

- [ ] 사용자가 AI 분석을 요청하면 Task가 생성된다.
- [ ] Task가 DB에 저장된다.
- [ ] 요청 직후 task_id가 반환된다.
- [ ] task_id를 기준으로 작업 상태를 추적할 수 있다.
- [ ] 하나의 Task가 어떤 원본 데이터와 연결되는지 설명할 수 있다.

### 5-3. Task 상태 관리

- [ ] PENDING 상태가 구현되어 있다.
- [ ] PROCESSING 상태가 구현되어 있다.
- [ ] SUCCESS 상태가 구현되어 있다.
- [ ] FAIL 상태가 구현되어 있다.
- [ ] 작업 시작 시 PROCESSING으로 변경된다.
- [ ] 작업 성공 시 SUCCESS로 변경된다.
- [ ] 작업 실패 시 FAIL로 변경된다.
- [ ] 실패 원인 또는 에러 메시지가 저장된다.

### 5-4. Task 상태 확인 API 또는 화면

- [ ] task_id 기반 상태 확인 API가 있다.
- [ ] 상태 확인 API가 실제로 동작한다.
- [ ] 프론트 또는 화면에서 상태를 확인할 수 있다.
- [ ] 완료된 작업의 결과 존재 여부를 확인할 수 있다.
- [ ] 실패한 작업의 에러 메시지를 확인할 수 있다.

상태 확인 API 예시:

```http
GET /tasks/{task_id}/status/
```
